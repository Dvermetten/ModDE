# Workstream 1: C++ Core with nanobind Bindings

## Objective
Move all per-generation computation (sampling, mutation, crossover, bound
correction, selection, adaptation, archive and population management) into
C++. Python keeps a thin, user-friendly layer: high-level API, ioh and
ConfigSpace integration, presets.

## What we take from modcma (and what we don't)

modcma is **inspiration, not a template** (decided 2026-11-19). Each of its
choices below is a starting point to weigh, not a default to copy.

modcma 1.2.0 was inspected for this plan (installed package, plus `setup.py`,
`pyproject.toml`, `CMakeLists.txt`, headers and workflows from GitHub).

| Aspect | modcma | Plan for modde |
|--------|--------|----------------|
| Binding library | **pybind11** (`Pybind11Extension`), *not* nanobind | **nanobind (decided, D-A1)** |
| Build | setuptools + `pybind11.setup_helpers`. A separate `CMakeLists.txt` only builds a C++ `main` executable. | **scikit-build-core + CMake** for both the extension and C++-only targets (decided, D-A2) |
| Linear algebra | Eigen, vendored in `external/` | **Eigen as a git submodule** in `external/eigen` (decided, D-A3) |
| C++ standard | C++17 | **C++17** (decided, D-A4) |
| Layout | `include/*.hpp`, `src/*.cpp`, `src/interface.cpp` (bindings), `external/` | Same |
| Configuration model | `Modules` (enums/bools) + `Settings` (numerics, `Settings(dim, modules, **numerics)`) → `Parameters` (runtime state holding `shared_ptr` strategy objects) → `ModularCMAES(parameters)` | Same three-level model (decided, D-A6) |
| Module dispatch | Abstract base struct per category (e.g. `bounds::BoundCorrection` with virtual `correct_x`) + factory `get(enum, ...)` returning `shared_ptr` | Same (decided, D-A7) |
| Step API | `run`, `step`, `mutate`, `select`, `recombine`, `adapt`, `break_conditions` | `run`, `step`, `mutate`, `crossover`, `correct_bounds`, `evaluate`, `select`, `adapt`, `break_conditions` (decided, D-A10) |
| Objective | `Callable[[Vector[m,1]], float]`, one call per individual | Batch evaluation by default with a `vectorized` flag, per-individual fallback (decided, D-A11) |
| Ask-tell | Python-only, not in C++ | Generation-level `ask()`/`tell(X, f)` on the split step API + per-individual Python wrapper (decided, D-A12) |
| High-level API | `fmin(func, x0, sigma0, budget, **kwargs)`, `settings_from_dict`, `settings_from_config`, `get_configspace` | Same set of functions |
| Wheels | cibuildwheel on ubuntu-22.04, windows-2022, macos-14. Linux builds with `-march=native`. | cibuildwheel, **Windows x64 + Linux x86_64 first**, Python ≥ 3.10, **no `-march=native`** (decided, D-A18). macOS/aarch64 later (FR-6). |
| Legacy Python | Kept, marked "no longer actively developed" | Kept as `modde.legacy` with a `DeprecationWarning`, frozen, removed once the new package is stable (decided, D-A5) |

## Core design

### Objects
- **`Modules`**: one field per module category, enum-typed (bool for on/off modules). No numerics.
- **`Settings`**: `dim`, `budget`, `lb`/`ub`, `target`, `seed`, `lambda0`, `F0`, `CR0`, `memory_size`, `archive_rate`, `p_best`, jDE/jSO constants, LPSR `lambda_min`, … plus `modules`. Every field is `std::optional`. Unset means "derive per the registry" (see WS3).
- **Resolution step**: `Settings::resolve()` fills derived values, validates the combination, and records the **provenance** of each value (`USER` / `DEFAULT` / `DERIVED(by=…)`). A user-set value is never overwritten. A conflict raises an error. This implements the WS3 policy in one place, shared by every frontend.
- **`Parameters`**: runtime state. Resolved settings, population, old population, archive, memory, RNG, stats, and the strategy objects (`shared_ptr<mutation::Strategy>` etc.).
- **`ModularDE`**: the step functions, `run`, `break_conditions`.

### One generation (target semantics, to be fixed in the spec)
```
mutate()          -> donor vectors V          (uses F, parents, archive, reference)
crossover()       -> trial vectors U          (uses CR, coordinate system)
correct_bounds()  -> U' + out-of-bounds mask  (no evaluation here; fixes KI-45)
evaluate(f)       -> f(U')                    (batch; budget-aware; fixes KI-8)
select()          -> population, improvement indices, successful F/CR
adapt()           -> archive, memory, F/CR sampling for next gen, population size
[oppositional_generation()]  (position/semantics per D-D11)
```
Each operator should be callable from Python on its own, as in modcma.

### Randomness (D-A13, decided)
- One engine per optimizer instance, seeded from `Settings.seed`.
- **Guarantee:** the same seed gives the same result on the same platform and version. No promise across platforms, so `std::*_distribution` may be used (its output differs between MSVC, libstdc++ and libc++). The user docs must state this.
- Route every random draw through one small RNG wrapper. This (a) lets tests inject fixed draws and compare operator outputs exactly against the spec (WS3), and (b) keeps cross-platform reproducibility possible later by swapping the distributions (FR-4).

### Evaluation and the GIL
- The objective is a Python callable in almost every use case, so each call crosses the C++/Python boundary. To keep this cheap:
  - Default to **batch evaluation**: pass the whole `n × d` trial matrix once per generation (ioh problems accept 2D input; verified with ioh 0.3.22).
  - Keep a per-individual mode for callables that only accept vectors, and for per-evaluation tracking via the ioh logger (D-B4). The mode is chosen with an explicit `vectorized` flag, not auto-detection (D-A11).
- Release the GIL inside pure C++ sections (`nb::gil_scoped_release`) so users can run several optimizers in Python threads. No parallelisation inside the core for 1.0 (D-A16).
- **Budget:** stop exactly at the budget (evaluate only part of the last generation) *if* this costs little compared with allowing overshoot. Measure it; otherwise allow overshoot and leave it to post-processing (D-A21).
- **Who counts evaluations (D-B3):** the problem does. The Python front end wraps plain callables with `ioh.wrap_problem` by default, and termination reads `problem.state.evaluations` / `state.final_target_found`. The C++ core stays ioh-free: it receives the objective callable plus an "evaluations used" query. The low-level API can pass a plain callable (counted by the core), which the speed tests use to measure ioh's per-evaluation overhead separately.

### Python ↔ C++ data
- Eigen dense type casters (`nanobind/eigen/dense.h`) for `Vector` and `Matrix`.
- Population layout (D-A9, decided): column-major `d × n` internally (each individual contiguous). The Python API exposes `n × d` everywhere, which is a breaking change from 0.0.4 and is accepted.
- Expose read-only views of internal state (population, F, CR, archive, memory) for analysis and tracking, without copying where nanobind allows it.

## Phase 2 status (2026-11-19)

All core modules are implemented in C++ against `dev/spec/` and exposed through
`modde._core` (split step API, n × d state views). Source layout:
`include/modde/{common,rng,modules,settings,population,sampling,parameters,operators,modde}.hpp`,
`src/{settings,sampling,sobol_directions,mutation,crossover,bounds,adaptation,modde,bindings}.cpp`.
`tools/gen_sobol_table.py` regenerates the Sobol table.

**First speed check** (Windows, MSVC 19.39, Python 3.11, one core; ioh BBOB f1, budget 2000·d, seed 1):

| Configuration | d | 0.0.4 | new: Python f, per point | new: vectorised f | new: ioh problem (batch) | speed-up vs 0.0.4 |
|---|---|---|---|---|---|---|
| classic DE | 10 | 0.06 s | 0.05 s | 0.01 s | 0.02 s | 3.2× |
| classic DE | 50 | 0.36 s | 0.46 s | 0.18 s | 0.25 s | 1.5× |
| L-SHADE (README config) | 10 | 0.43 s | 0.06 s | 0.02 s | 0.03 s | 14.9× |
| L-SHADE (README config) | 50 | 8.53 s | 0.45 s | 0.20 s | 0.26 s | 33.0× |

- Core-only overhead (objective returns zeros): 0.5–3 µs per evaluation, ≈ 25–40 ns per coordinate, independent of the configuration.
- 0.0.4's classic DE was already mostly vectorised NumPy, and the evaluation itself is a large share of its runtime, so the gain there is small. The ≈20× target (D-A19) is met for adaptive configurations, not for plain DE. Per D-A19, no complexity was added to chase it. The remaining per-coordinate cost is the crossover's uniform draws and the bound checks; revisit with a profiler in Phase 4 if needed.
- Batch evaluation (D-A11) is 2–3× faster than one Python call per point, as expected.
- Note: classic DE differs between the columns' algorithms (0.0.4 CR = 0.5, new default CR0 = 0.9, D-D2); timing is comparable, precision is not.

**Deferred from Phase 2 (by decision or to Phase 3):**
- GIL release around pure C++ sections (D-A16): not done yet; the objective is always called with the GIL held.
- Python-overridable hooks (D-A8): `Sampler`, `BoundCorrection` and `Mutation` are virtual base classes, but no trampolines are bound yet.
- Pickling / serialisation of `Settings`, the public API (`fmin`, presets, ioh wrapping, ConfigSpace), ask-tell, stubs: Phase 3.

## Build and distribution
- `pyproject.toml` using `scikit-build-core`, with `nanobind` as a build requirement.
- `CMakeLists.txt`: `find_package(nanobind CONFIG REQUIRED)`, `nanobind_add_module(_core STABLE_ABI NB_STATIC src/...)`, `nanobind_add_stub(...)` to generate `_core.pyi`.
- Compiler flags: `-O3` / `/O2`. No `-march=native` in wheels. Maybe an opt-in CMake option for local builds.
- Python ≥ 3.10. CI tests on Windows x64 + Linux x86_64 with Python 3.11 (matches the main development machine). cibuildwheel for the same two platforms first; nanobind's stable-ABI support means Python 3.12+ needs only one wheel per platform. macOS/aarch64 later (FR-6).
- An optional C++-only target (benchmark/driver), like modcma's `main`. This allows profiling without Python and, potentially, linking the header-only IOHexperimenter C++ library directly (D-B5).

## Risks
- **Bit-exact parity with 0.0.4 is not achievable.** The RNG and QMC scrambling will differ. Parity is checked at operator level (injected draws) and statistically at run level.
- **Per-evaluation hooks** (the ioh logger tracking F/CR per individual) and **batch evaluation** pull in opposite directions. ⚠️ **Keep this in mind when implementing the evaluation path** (D-B4, deferred to implementation). The chosen design must pass the logging validation in [03_module_validation.md §5.3a](03_module_validation.md#53a-ioh-logging-validation).
- **Python-implemented modules** (custom mutation written in Python) need nanobind trampolines and cost speed. 1.0 offers only selected hooks: sampler, bound correction, mutation (D-A8). Base classes are designed binding-friendly so more can follow (FR-2).
